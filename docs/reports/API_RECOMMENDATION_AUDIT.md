# API and recommendation audit

**Repository** Academic_Advisor_Stable  
**Date** 2026-11-18  
**Status** PASS WITH WARNINGS — audit complete, two reproducible unit test failures

## Scope and conclusion

Read all **20 Python files under `src/api`** and **14 under `src/recommendation`**, including four package initializers and four compatibility modules. The two scoped trees contain one recommendation engine. The combined HTTP routes and the split intake workflow converge before candidate generation. Direct evaluation uses a different factory and can select different ranking strategies, but runs the same engine. The documented observed-plan UI describes an already registered plan and lies outside this audit.

The most concrete duplication is the API's student feature derivation, repeated history validation and loading, and an academic sort immediately followed by the actual final ranker. The main boundary issue is that registration credit-policy construction and several serving decisions live in `ApiService` and the API adapters. The API files with the clearest consolidation case are the four import-only aliases. Their removal still needs caller evidence.

Evidence uses repository-relative paths and source line numbers. Caller claims refer to in-scope Python imports and calls, plus relevant test and documentation references. Other production source trees, deployment scripts and downstream packages were outside the inspection boundary. A missing reference in this audit is evidence to investigate, especially for a public name.

## Findings and consolidation evidence

### F01. Registration policy is constructed in the API

`ApiService._build_engine_request()` (`src/api/service.py:346–377`) intersects provider/request ranges, selects the exact target and synthesizes caps. `validators.courses._rules()` (`src/api/validators/courses.py:205–225`) derives the effective load profile. `adapters.courses._course()` (`src/api/adapters/courses.py:41–67`) computes group remaining credits, and `src/recommendation/constraints.py:37–67,115–185` separately normalizes typed cap inputs and enforces the final hard limits. A remaining-credit expression appears in both layers, with different inputs and behavior for strict excess, overflow, reservations and unbounded groups. Put the typed policy calculation in the recommendation package while retaining provider-specific evidence checks and error translation at the boundary. Preserve the current type-total behavior. There is no authority in this code to infer a separate university type cap.

### F02. Student snapshot feature derivation has two owners

`add_snapshot_features()` (`src/api/adapters/student.py:143–147`) computes semester, GPA trend and missing flag. `normalize_student_payload()` (`src/recommendation/inputs.py:87–115`) recomputes the same features after selecting `BACKEND_SNAPSHOT_COLUMNS`, which excludes the derived fields. API `None` and core `NaN` become equivalent missing indicators for inference, but the constructed snapshot and validation `field_readiness` summaries differ if the API fields disappear. A shared pure derivation can support both contracts. Prior GPA eligibility/denominator attestation is a different concern tied to PHP field names and reference dates. `add_history_features()` already delegates GPA lags to shared feature routines. Its gap logic and `build_student_snapshot()`'s failure-credit ratio are model-facing calculations still owned by the API.

### F03. Serving policy and history loading repeat across layers

`src/api/service.py:132–191,194–206,316–343` and `src/recommendation/two_stage_engine.py:107–123,182–203`. API startup and history compatibility contain the same Pareto-at-both-stages predicate. Artifact loading validates the manifest's approval shape. The engine factory separately requires positive approval. `TwoStagePlanRecommender.load()` then repeats that requirement in `from_loaded_artifacts()`. The API recommendation context refreshes the manager, calls `health()` (which refreshes again), validates history selection and preflight-captures. The engine captures again for scoring. The cumulative proxy rereads control and can reload active/exact bundles on these operations (`cumulative_history.py:184–193,443–481`). Even legacy managers repeat selection checks. The API preflight and engine capture can observe different pointers when another worker activates history. Each individual inference still uses a pinned object. Preserve the direct-core cutoff/top-K/approval checks and the API’s granular errors. Consolidate readiness and one request-owned serving history selection instead of dropping a validation layer. The API separately loads a GradeScale for diagnostic independence, while artifacts hash and load their own scale (`service.py:168–191` and `two_stage_artifacts.py:273–276`). That is a justified independent readiness path, with a compatibility question for injected or divergent assets.

### F04. Final scoring performs a redundant preliminary rank

`summarize_scored_plans()` calls `rank_plans()` (`src/recommendation/plan_scoring.py:47–51,70–90`). The engine merges one row per plan and calls `rank_evaluation_plans()`, which rebuilds its own academic reference and deterministic identity tie-break (`src/recommendation/two_stage_engine.py:226–235` and `ranking.py:122–135,180–209`). For the engine, full final ranking supersedes the preliminary sort. The legacy scorer sorts by raw `plan_id`, and the current ranker requires canonical hashed IDs. A behavior-preserving refactor can expose aggregation without ordering to the engine and retain sorted results for any standalone caller that needs the original order. `rank_academic_reference()` is a separately tested diagnostic and shares the current comparator.

### F05. Stage 1 and Stage 2 compute overlapping plan metrics

`build_stage1_shortlist()` (`src/recommendation/shortlist.py:33–53`) and `summarize_scored_plans()` (`src/recommendation/plan_scoring.py:70–90`) both compute weighted quality points, expected failed credits, plan GPA, projected GPA, expected gain, improvement and legacy `gpa_gain`. They already share `project_cumulative_gpa()`. Stage 1 uses exact Fraction-weighted aggregation. Stage 2 aggregates float course rows with pandas. The standalone scorer flags repeats by attempt number, and the engine ORs in non-`NEW` status (`two_stage_engine.py:232–233`). Stage 1 already uses both. Share the derived metric semantics where possible, while retaining those numerical and standalone-contract differences. Keep both prediction passes.

### F06. The shortlist cap bounds Stage 2 only

`shortlist.build_stage1_shortlist()` (`src/recommendation/shortlist.py:31–59`) retains every feasible plan record and index tuple before ranking. For every feasible plan `compute_balance_components()` (`src/recommendation/balance_policy.py:29–47,63–99`) validates and normalizes the same full eligible set again. `ranking._pareto_levels()` (`src/recommendation/ranking.py:138–164`) compares scoped plan pairs, quadratic in their count where Balance is active, and stores dominance edges. `constraints.enumerate_feasible_plan_indices()` applies caps only after the exact search produces a subset. These are potential latency/memory costs identified from the implementation. The API's candidate limit applies only in the configured performance-test mode. A request-owned cache of immutable eligible-set Balance data can remove repeated work. Pruning or rank/search changes require output and performance evidence.

### F07. Compatibility modules implement no behavior

`src/api/{validation,student_adapter,courses_adapter,history_adapter}.py:1–5` only forward exports. `ApiService` and the route import canonical modules. No test import, in-scope consumer or relevant current documentation was found using these paths. The student and course shims also expose private names. They are concrete removal candidates after checking out-of-scope and deployment consumers, with no source deletion justified solely by the scoped absence. The three API initializers and the recommendation initializer are package markers or docstrings.

### F08. History wire handling and delta normalization repeat

`validate_finalization()` (`src/api/validators/history.py:28–35`) and `ApiService._finalized_payload()` (`src/api/service.py:225–236`) both check attestation part and approval reference and differ in requiredness and workflow. `adapt_history_delta()` plus `validate_delta_contract()` normalize for public diagnostics, and the optional `preview_delta()` normalizes again. `CumulativeHistoryStore._preview()` normalizes before delegating to the manager, and `_commit()` normalizes before publication normalizes again. `finalize()` adds a preliminary normalization as well. See `src/api/adapters/history.py:8–29`, `validators/history.py:20–43` and `src/recommendation/{cumulative_history.py:330–441,history_update.py:323–359}`. A common HTTP translator and private normalized-delta operations can share rules. The read-only diagnostic, durable pending preview, verified publication and durable activation have distinct effects. Keep separate tests for them and use the same immutable normalized rows throughout a single operation. Also preserve direct-store enforcement of confirmation, modes, lineage, and locks. `_ServingHistoryManager` subclasses `FrozenHistoryManager` for engine compatibility without initializing its writable state (`cumulative_history.py:472–491`, `two_stage_engine.py:91–99`). A narrow snapshot-reader interface is worth reviewing after caller coverage, especially for fault-injection and update tests.

### F09. Split validation and structural checks have intentional layers

`app.py:148–156` already validates split HTTP models, then `service.py:63–89` validates the same envelope as a dictionary and re-runs both semantic adapters on the assembled request. This has a cost but protects direct service callers, validates a component before persistence and checks the merged evidence at inference. Preserve the replay-before-semantic-validation behavior. `schemas.py:96–102` repeats the request ID constraint for both models, and `request_store.validate_request_id()` (`request_store.py:30–33`) enforces it again for store/lookup callers. A shared pattern can prevent drift while keeping call-site-specific errors. Byte checks in `app.DecimalRoute` and `RequestStore._payload()` bound incoming bytes and typed storage respectively. They should stay distinct. `validate_delta_rows()` and core `normalize_history_delta()` likewise enforce different input type contracts. A blanket deduplication would change accepted inputs or error surfaces.

### F10. Eligibility and constraint checks overlap without being interchangeable

`validate_course_fields()` (`src/api/validators/courses.py:73–100`) requires literal provider Y/N flags. `inputs._explicitly_ineligible()` (`src/recommendation/inputs.py:118–169`) accepts an optional, wider ready-payload vocabulary. The API sends neither flag after filtering. Raw duplicate detection happens before a provider row can be filtered. Adapter deduplication compares normalized records and the reason. Direct-core normalization rejects any surviving duplicate ID. These are useful boundary guarantees. Similarly, `RecommendationOptions.credit_mode()` rejects exact plus range, whereas direct `normalize_request_payload()` can accept exact plus a valid range and uses the exact value. The core also enforces a positive target in `PlanConstraints`. That difference is tested, and collapsing the validators would change accepted ready inputs. `validators.courses.validate_previous_course_status()` correctly delegates the vocabulary to `course_status.normalize_previous_status()`, but `constraints._CANDIDATE_GROUPS` duplicates the set implied by `course_status.CANDIDATE_GROUPS` plus `OTHER_PREVIOUS`. Balance imports this private set and `_credit_value`. Place the vocabulary under one owner and keep source attestation and ready-payload normalization separate.

### F11. Unused-looking surfaces need scoped treatment

- `src/recommendation/plan_scoring.py:93–96`. `empty_summaries()` has no scoped caller or relevant test reference. The Stage 1 empty branch constructs a frame with extra columns. Verify external scoring/evaluation use before removal.

### F12. Shared primitives should retain distinct contracts

Exact signed Decimal sums already have one implementation in `src/recommendation/plan_generation.py:7–22`. ID, numeric, semester and eligibility validation across API and core differ in accepted types, provenance and error shape. For example, `validators.common.identifier()` requires strings while ready IDs use `clean_id`. Delta counts enforce exact float64 integer bounds (`history_update.py:42–61`). HTTP `json_safe()`, split-store tagged serialization, engine `_json_value()` and delta `_canonical_number()` serve different wire, replay, fingerprint and hash contracts. The engine and delta separately implement normalized Decimal text. Share that small primitive only with hash parity evidence. Keep the codec boundaries and their callers' choices for type tags, precision and missing values.
